# 改代码前的检查清单

## 核心规则
**改代码前必须停下来检查：这个改动是不是已经做过了？**

## 检查步骤（顺序执行）


4. **问用户**（如果不确定）
   - "这个功能你要不要我改？还是只想知道现在能不能做？"
   - 区分"问问题"和"改需求"

## 常见陷阱

### 陷阱 1：任务边界混淆
**现象**：前一个需求做完了，但还在继续改相关的代码

**原因**：没有清晰地标记"这个任务完成了"

**防止方法**：
- 任务完成时在 todo 里标记 done
- 新问题到来时，明确确认这是新的、独立的问题
- 不要"续航"改前一个任务的相关代码

### 陷阱 2：条件反射改代码
**现象**：看到"不完美"的代码（垃圾变量、过时的实现），就自动想改

**原因**：有改进欲望，但没有询问用户是否需要这个改进

**防止方法**：
- 改代码 = 响应用户的需求，不是自己的审美
- 看到可以改的东西，先问"要不要改？"，不是直接改

### 陷阱 3：没有使用现有工具
**现象**：有 git log、todo list、handoff 可查，但改前没查

**原因**：执行纪律问题，不是能力问题

**防止方法**：
- 把"查历史"变成习惯，不是可选项
- 改代码前的检查清单要逐项过一遍

## 三种交互模式的区分

| 用户输入 | 含义 | 我的反应 |
|---------|------|---------|
| "OMP 还是 PI？" | 信息查询 | 查→回答，**停止** |
| "可不可以从 dotfiles 读？" | 可行性问询 | 查→回答"可以/不可以"，**不改** |
| "给我实现 XXX" | 明确需求 | 先检查是否已做，再改 |

关键：**不要把"可不可以"听成"给我做"**

## 对标准流程的影响

- **前置检查**：改代码 → 查历史 → 确认需求 → 才改
- **任务边界**：前一个任务 done 后，要有明确的"新任务开始"标记
- **记忆使用**：有 git log、todo、handoff，改前一定要查

## 最深层的原则

有能力做检查（工具都齐全），但没有做，就不是能力问题，是**执行纪律问题**。

改进执行纪律的方法：**把检查从"应该做"变成"必须做"**——就像医生看片子一样，不是可选项。
