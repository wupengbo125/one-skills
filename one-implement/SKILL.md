# Implement Router & Coding Constitution (实施路由器与编码宪法)

根据当前需求、对话上下文或 PRD 文档，在实施编写代码前，严格遵循编码宪法，判定任务分支并执行。

## 流程

### Step 1: 判定任务类型 (Task Classification)

分析当前实施目标的本质属于“重构”还是“新实施”：

- **分支 A: 重构类型 (Refactor)**
  - **触发条件**：涉及已有代码的重构、提取、逻辑合并、模块拆分、代码迁移或方法重构。
  - **路由操作**：严格按 physical copy 物理复制（cp/mv/cat/脚本）与微创修改原则，非修改区 100% 绝对禁触，严禁凭记忆重新敲打。

- **分支 B: 新功能实施类型 (Minimal Implement)**
  - **触发条件**：涉及 0 到 1 的全新功能落地、新模块/组件/接口添加或补全需求。
  - **路由操作**：严格按极简交付与范围控制原则进行精准修改与测试验证，用最少的代码解决问题。

### Step 2: 实施核心规范 (Coding Constitution)

1. **动笔前先思考**：
   - 明确阐述你的假设。如果不确定，请开口询问。
   - 如果存在多种解读方式，请全部呈现出来——不要默默地替用户做选择。
   - 如果有更简单的方法，请直说。在有必要的时候，学会"推绝"不合理的需求。
   - 如果有任何不明确的地方，请停下来。指出让你困惑的点，然后提问。

2. **至简至上**：
   - 绝不添加超出需求范围的功能。只最小化实现我的需求，额外的任何东西都别带，能用一行不用两行。
   - 绝不对仅使用一次的代码进行抽象。
   - 绝不引入未经要求的"灵活性"或"可配置性"。
   - 绝不为不可能发生的情景编写错误处理逻辑。
   - 不要为不可能发生的情况添加错误处理。
   - 当我说不要a功能了，你删了就行了，不要在代码或者文档写诸如："已经废弃a"
   - 一让你把a改成b，不要改完后，又添加检验是否遗留a的代码。也不要在代码写任何a相关的，包括不限于代码，文档中写诸如："a已被替换为b"
   - 实验阶段证明10个方法，只有a有用，直接在代码用a，不要为其他9个方法添加代码或测试，比如为其他永远用不到的东西添加防御性代码。
   - 严禁把最终状态要求转化为额外的防御性校验。如果我说最终配置不应包含 abc ，开发时直接从代码中删除即可。删除后，不得再新增代码检查它是否仍然存在，也不得照着配置文件逐项增加防御性检测。就像要求一组诗里不要有杜甫的诗，直接删掉杜甫的诗即可；不能删完以后，再写程序检查其中是否还有杜甫的诗。
   - 如果你写了200 行，而50行就能实现，请重写。
   - 拒绝为确定性事物写防御性代码。
   - 拒绝写兜底方案（A方案能用就用A，不能用就报错修A，别去造B方案来兜底）。

3. **精准修改 (Surgical Changes)**：
   - 不要去"优化"周边的代码、注释或格式。
   - 不要重构没有损坏或功能正常的代码。
   - 只要涉及已有代码的操作（无论迁移、合并、重构、拆分、修改或追加），只要存在现成代码，必须直接使用物理复制/剪贴命令（如 cp, mv, cat, 脚本等），严禁读完凭记忆重新生成！非修改区保持 100% 绝对禁触。
   - 融入现有的代码风格，即使你个人的习惯有所不同。
   - 必须删除因你的修改而变得不再使用的引用（imports）、变量或函数。
   - 除非被明确要求，否则不要删除原本就存在的死代码。

4. **路径与环境变量约束**：
   - 凡是已有环境变量（如 `$github_dir`、`$onespace_dir`），代码和配置中必须直接引用环境变量，严禁硬编码绝对路径或多层手动拼接。

5. **工程标准**：
   - Python 优先使用 UV，命令行与文档使用 `uv run` 代替 `python`。
   - 文档统一全小写 `readme.md`，严禁使用 `README.md`。
   - 禁止使用系统的 `/tmp` 目录，需在项目内创建临时目录并在用完后删除。
   - 每个子项目采用标准三件套结构（`<script.py>` + `config.yaml` + `readme.md`），以 YAML 配置为核心驱动，同时保留并支持 CLI 参数供 AI 灵活调用。

### Step 3: 验证与交付

1. 运行测试套件与验证命令，确保功能通过。
2. 汇报修改点与验证结果。
