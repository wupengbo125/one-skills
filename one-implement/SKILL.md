# Implement Router

根据当前需求、对话上下文或 PRD 文档，进行任务类型分支判定并自动路由到对应的实施 Skill。

## 流程

### Step 1: 判定任务类型 (Task Classification)

分析当前实施目标的本质属于“重构”还是“新实施”：

- **分支 A: 重构类型 (Refactor)**
  - **触发条件**：涉及已有代码的重构、提取、逻辑合并、模块拆分、代码迁移或方法重构。
  - **操作概要**: 严禁阅读了代码，重新写。而理解了代码，像人类程序员一样，复制原代码，然后粘贴。而非重新手写，那样一定会漏掉东西
  - **操作详情**：调用skill： `/one-refactor-implement`，严格按 physical copy 物理复制 5 步规范与剪贴板优先原则进行微创修改。
  - **测试**: 进行diff比对。确保能复制的地方都是字符级一样。不一样的都是业务需求要改的。

- **分支 B: 新功能实施类型 (Minimal Implement)**
  - **触发条件**：涉及 0 到 1 的全新功能落地、新模块/组件/接口添加或补全需求。
  - **操作概要**: ① 精准忠实交付，不超范围 → ② 极简代码，能简不繁。
  - **操作详情**：调用 skill： `/one-minimal-implement`，严格按极简交付与范围控制原则进行精准修改与测试验证。
  - **测试**: 对照用户说的需求，多出的任何功能都算测试失败。

- **完成标准**：准确判定分支并完整执行对应 Skill 的交付规范。

### Step 2: 实施核心规范

**至简至上**：
- 绝不添加超出需求范围的功能，能用一行不用两行。
- 绝不对仅使用一次的代码进行抽象。
- 绝不引入未经要求的"灵活性"或"可配置性"。
- 拒绝为确定性事物写防御性代码。
- 拒绝写兜底方案（A方案能用就用A，不能用就报错修A，别去造B方案来兜底）。
- 凡是已有环境变量（如 `$github_dir`、`$onespace_dir`），严禁硬编码绝对路径，必须直接引用环境变量。

**精准修改**：
- 不要去"优化"周边的代码、注释或格式。
- 不要重构没有损坏或功能正常的代码。
- 只要涉及已有代码，必须直接使用物理复制/剪贴命令（如 `cp`, `mv`, `cat`），严禁读完凭记忆重新生成！非修改区 100% 禁触。
- 融入现有的代码风格。
- 必须删除因你的修改而变得不再使用的引用、变量或函数。
- 除非被明确要求，否则不要删除原本就存在的死代码。

### Step 3: 验证与交付

1. 运行测试套件与验证命令，确保功能通过。
2. 汇报修改点与验证结果。
