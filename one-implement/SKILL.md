# 代码开发与实施流程 (Implementation & Workflow)

编写、修改、重构代码时的**唯一总入口**。
通过隔离实现与双轴审查，彻底杜绝 AI 自作主张、过度抽象与范围蔓延。

---

## 核心流程五步法

```
用户提需求
   │
   ▼
1. 需求受理与锚定（主 Agent：提取 Target 与 Non-Goals，绝不无故打扰盘问）
   │
   ▼
2. 隔离实现（派 Sub-agent 1：戴锁编码，严格遵守《编码实施守则》）
   │
   ▼
3. 测试验证（Sub-agent 1 或主 Agent：跑最小针对性测试，确保可运行）
   │
   ▼
4. 双轴审查（派 Sub-agent 2 & 3 并行审查 git diff HEAD）
   ├── Reviewer A（Standards 轴）：严查 Speculative Generality（投机抽象）、坏味道
   └── Reviewer B（Scope 轴）：严查 Scope Creep（范围蔓延）、未要求代码、自作主张
   │
   ▼
5. 需求核对与交付（确认无误后写海马体记忆，commit 并交付）
```

---

## 一、需求受理与锚定（改代码前）

1. **直接提取意图**：从用户的一句话或文档中，提炼出两项关键边界：
   - **Target（核心目标）**：必须达成的最小功能。
   - **Non-Goals（非目标/坚决不做）**：顺带发现但不属于本次需求的代码、无明确要求的多余抽象、过度防御代码。
2. **拒绝无故小盘问**：不要像开需求会一样逼问用户无关细节，直接按默认最佳实践收拢需求，快速进入实现。

---

## 二、隔离实现（改代码中）

派发一个独立的 Sub-agent 执行编码，使其脱离主会话冗余上下文，并在其 Prompt 中严格注入以下《编码实施守则》：

### 1. 至简至上 (Simplicity First)
- **拒绝为确定性事物写防御性代码**：环境已知、文件必定存在时，直接读取，绝不写多余 `try-catch` 或假防御。
- **拒绝写回退兜底方案**：禁止写“A 不行就尝试 B，B 不行就尝试 C”的脆弱代码；直接使用正统方案 A，出错直接修 A。
- **路径明确**：优先使用确定的绝对路径或 `~/`，避免猜测脆弱的环境变量。

### 2. 精准修改 (Surgical Changes)
- **改 A 只改 A**：需求让改文件 A，绝不顺手去格式化文件 B，绝不借机做“顺便重构”。
- **严禁投机抽象 (No Speculative Generality)**：严禁为“未来可能需要”创建单实现的 Interface、工厂类、配置字典。
- **短小精悍**：能一行代码搞定绝不写五十行，标准库有的绝不手写。

### 3. 重构前置判定
仅当用户明确要求重构时方可重构；修改功能时，保持既有架构形态，绝不擅自扩大破坏面。

---

## 三、测试验证（改代码后）

- 修改完成后必须运行一次最小针对性测试（单测、脚本或 CLI 验证），证明修改生效。
- 绝不跑与修改完全不相关的全量慢速测试，快速反馈。

---

## 四、双轴 Code Review（双 Sub-agent 并行审查）

开发完成后，自动抓取 `git diff HEAD`（无需用户提供 Commit SHA 或分支），派发两个互无记忆偏见的独立 Sub-agent 并行审查：

### 1. Sub-agent A（Standards 轴：代码质量与反过度设计）
对照行业标准与 Matt Pocock 坏味道清单进行审查：
- **Speculative Generality**：有没有为了“以后”加了多余参数、钩子或无用类？有则标红打回。
- **Duplicated Code**：是否有重复代码？
- **Middle Man**：是否有纯转发的无用中间函数？
- **冗余防御**：是否有无意义的兜底判断？

### 2. Sub-agent B（Scope 轴：需求符合与反范围蔓延）
直接对照第 1 步的原始需求进行苛刻审查：
- **Scope Creep（重点审查）**：Diff 里的改动，用户说了吗？
  - 改了不相干的文件 ➔ **打回**。
  - 顺手改了无关函数的实现 ➔ **打回**。
  - 加了需求之外的“小彩蛋/小功能” ➔ **打回**。
- **需求漏做**：用户要求做的是否全部有对应代码？

---

## 五、核对与交付（最终闸门）

1. **审查打回处理**：
   - 任一 Reviewer 发现范围蔓延（多开发）或投机抽象，立即删除多余代码，重新跑 Diff。
2. **宪法级记忆落盘**：
   - 确认代码精简无误后，先按宪法向 `one-hippocampus` 追加今日流水，同步索引。
3. **本地 Commit 并 Push**：
   - 提交精炼 commit，向用户交付结果。
