# Build Blueprint

把用户指定的材料整理成独立的业务白盒。只生成或更新目标蓝图，不负责规定、生产、维护或验证材料来源。

## 核心规则

1. 仅在用户明确要求时生成蓝图；只使用用户给定的口述、会话、代码、文档、设计稿或其他材料，不擅自增加来源。
2. 蓝图作用域可以是整个仓库、单个目录、多个目录或跨目录业务；蓝图之间没有父子、继承或覆盖关系。
3. 只写业务目标、功能、行为、UI、规则与边界，不写文件结构和代码实现。
4. 只修改用户指定的目标蓝图，不修改 MAP、PRD、ADR、README、Agent 导航、输入材料或其他蓝图。
5. 简单蓝图保持简短，不为填满模板假造内容；不得写入密钥、凭据或个人数据。

## 流程

### 1. 确定范围与位置

确定业务名称、作用域、输出位置以及创建或更新。不要把当前工作区自动当成整个仓库；无法判断作用域时，只询问用户要为整个仓库还是哪个目录/业务生成。

- 整个仓库：根目录 `BLUEPRINT.md`。
- 单个目录：该目录的 `BLUEPRINT.md`。
- 多目录或跨目录业务：`docs/blueprints/<业务名>.md`。
- 用户指定位置时，以用户指定为准。

作用域只说明蓝图描述范围，不建立文档层级。

### 2. 使用材料

直接使用用户指定的单一或多种材料。材料不足以形成有意义的蓝图时，只询问缺失的业务内容。

### 3. 生成或更新

读取同目录的 `BLUEPRINT-TEMPLATE.md`，按内容灵活裁剪：

- 产品或应用：目标、用户、功能、UI、规则与边界。
- 业务能力：触发、行为、结果、规则与限制。
- 量化策略：市场、数据、信号、仓位/风险、输出与评估。
- 独立工具：使用者、问题、输入、行为、输出与限制。
- 混合仓库：仓库定位、互不相关的独立能力、公共约束；不得编造统一流程。

Frontmatter 必须记录精确 `scope`，整个仓库使用 `.`。正文按功能或用户行为组织；功能尽可能是说明使用者、触发、行为和结果；UI 仅在材料包含或用户要求时保留；约束只影响产品行为的内容。

更新时只根据本次材料修改相关内容；未要求重写时，保留材料未涉及的现有内容。

### 4. 交付

只报告目标蓝图路径、作用域、写入的功能或 UI，并说明其他蓝图未改；不要粘贴整份蓝图。

## 完成标准

- 作用域明确写入 frontmatter。
- 蓝图独立成立，主要功能和边界清晰。
- 正文没有退化成目录索引、代码导览或实现说明。
- 没有擅自增加或验证来源。
- 除目标蓝图外没有修改其他文件。
