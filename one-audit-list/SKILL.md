# one-audit-list

## 干什么

把**这一轮工作积累的所有需求**写进派活时给你的那个需求文档路径（提示词末尾写着「需求文档路径：…」，文件名是 `audit-list.md`）——从上次提交/评审到现在，用户提过的每一条都算，不是最后一句对话的小需求。

写它的人是你（干活的那匹马）；读它的人是评审员——它评审的就是这段时间工作区里的全部改动，清单必须和改动一条条对得上，少写一条，评审员就把那处改动当成跑偏。

路径由派活的插件指定、每匹马一份，互不干扰；提示词里没给路径就先问我，别自己挑地方。

## 步骤

1. 在提示词给的那个需求文档路径上写清单（文件已存在就整个覆盖重写，目录不存在先建目录）。
   完成标准：清单覆盖工作区里当前的全部改动，一条不多、一条不少。
2. 整体三节，每条需求写清目标、判据、约束：

   ```
   # 需求清单

   ## 要做什么
   ## 做到什么程度
   ## 约束
   ```

   完成标准：评审员拿着改动逐条对，每处改动都能在清单里找到理由，清单里每条也都能在改动里看到落点。
3. 需求变了、加了新需求、或某条做完——回头重写整份清单。
   完成标准：文件内容和工作区里实际攒着的改动一致。

## 记起点提交（用户让你记 ID 时才走）

用户让你“记 ID / 记录提交 ID”这类话时，做两件事，然后回到写清单：

1. 同步仓库：该提交的提交、拉取远端，确认工作区干净、代码是最新的。
   拿不准（有没提交的改动、拉不下来）就问一句，别硬来。
2. 把当时的提交 ID 写成清单里的一行（如 `起点提交：abc1234`）。
   清单里已经有这一行就不动它——同一轮多写几次会把起点越推越后，前面做过的改动就掉出本轮了。

用户没说记 ID 就别记，这一行不是清单的必备内容。

## 为什么覆盖而不是追加

清单代表**当前工作区里的全部待审改动**。追加会让它越长越乱——已提交、已撤销的还挂在上面，评审员分不清哪些还算数。覆盖 = 每次重写全量：还在的留下，不在的删掉。名字固定同理，每轮换个名字，项目里堆一地。

## 写什么

需求必须且只能来自于**经用户确认的平铺 Plan**，尽量沿用原话，严禁自己脑补。
多轮会话将每次用户同意的平铺 Plan 进行融合；若后轮修改了某些项，直接刷掉前面的条目，而不是追加。
每条需求严格对应平铺 Plan 写清**要做什么、做到什么程度、约束**——评审员拿它当判据。实现方案与过程不写。

## 常见跑偏

| 跑偏 | 正解 |
| --- | --- |
| 只写最后一句对话的小需求 | 全量清单，覆盖工作区全部改动 |
| 追加一段"这次又加了…" | 整个重写，清掉已不在工作区的条目 |
| 自己挑个地方写文档 | 写到提示词给的那个路径 |
| 把实现方案和踩坑过程写进去 | 每条只写目标、判据、约束 |
| 等评审时才补一份 | 需求一出就更新，评审前它必须是全的 |
| 清单里已有起点提交还重写它 | 保持原样，只有用户让你重记才更新 |
