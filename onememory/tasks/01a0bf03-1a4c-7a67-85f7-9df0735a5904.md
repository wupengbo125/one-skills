# 会话 01a0bf03-1a4c-7a67-85f7-9df0735a5904（2026-09-20 21:40~22:30）

## 背景诉求

用户报「从 Windows（redmi-w）连本机 one 很慢」，并追问：
1. 为什么 tailscale 地址成了 IPv6？不想要这个地址；
2. 昨天（09-19）改了 frp 相关的东西，怀疑是它导致的；
3. 后来补充：手机连本机快、Windows 慢；用的方式是 SSH；Windows 无 exit node、代理非 TUN 模式、退出代理进程仍卡。

## 排查过程（含走过的弯路）

### 弯路一：误判为 frp 被 mihomo TUN 劫持（方向对了一半，因果搞反）

先发现 frpc→frps（192.140.188.104:7000）连接本地地址是 `198.18.0.1`（mihomo TUN 网段），
`ss -tni` 显示 delivery_rate 仅 1.6Mbps、cwnd=1、DSACK/乱序/重传暴增 → 判断「frp 通道卡」。
据此给 mihomo 加 `tun.route-exclude-address: [192.140.188.104/32]` 并重启 mihomo + frpc。
**这个修复本身是对的**（mss 8948→1398、经 frp 的 SSH 0.53s 返回），但**不是用户抱怨的慢的来源**。

### 弯路二：把「快的」和「慢的」两条路搞反

第一次回答时断言「frp 卡、tailscale 直连才快」，与用户实际体感完全相反（用户：frp 快、tailscale 卡），
被用户纠正。教训：**先问清用户说的是哪条路，再下结论。**

### 定位

- `tailscale status`：两台设备都走 direct IPv6，且**同一 /64**（`2409:8a70:4022:5811`，中国移动）；
  本机公网 IPv6 是 `240e:982:4200:1001::369`（中国电信）→ **跨运营商 IPv6**。
- 反复 ping 两台设备，丢包在 0%~33% 之间随机跳，**同一时刻一台 0% 另一台 20%，会互换** → 丢包是链路波动，不是某台设备的问题。
- Windows 侧 `tailscale ping one` = **direct IPv6，9ms**（延迟极低），`netcheck` 里自建 frp DERP 可用（72.6ms）。
  → tailscale 数据面没问题，罪在**丢包**；SSH 对丢包零容忍，故表现为「延迟 9ms 却卡到动不了」。
- frp 那条走 IPv4（`192.140.188.104`），实测 0% 丢包、23~35ms → 一直稳定快。
- 排除项：exit node（用户确认未选）、Windows 代理（非 TUN 模式，退出进程仍卡）、MTU（tailscale0 = 1280 正常，大小包对比无异常）。

### 用户追问的「昨天改了啥」

查到是 `/etc/sysctl.d/99-tailscale.conf`（2026-09-19 19:51，`net.ipv4.ip_forward=1` + `net.ipv6.conf.all.forwarding=1`），
起因是 tailscale 报 `Subnet routing is enabled, but IP forwarding is disabled`（本机 advertise 了 `0.0.0.0/0` + `::/0` 当 exit node）。
该改动只是「让被当出口」的能力生效，**不是丢包的成因**。
记忆位置：`one-hippocampus/memory/2026-09/2026-09-19.md` 20:01 那条；卷轴第 6 节告警。

## 关键决策

- **不关闭 IPv6**：Tailscale 官方**没有**关闭 tailnet IPv6 的开关（仅 feature request tailscale/tailscale#13705），
  要「改 IPv4」只能禁用网卡 IPv6（Windows 侧 `Disable-NetAdapterBinding ... ms_tcpip6`，或本机禁 ens3 IPv6），
  代价是整机失去 IPv6。用户最终**决定先不折腾**，维持现状。
- 给用户的替代建议：既然 frp 稳，SSH 直接走 frp（`ssh -p 10001 ctyun@192.140.188.104`），tailscale 留给 tailscale serve 的网页服务。
