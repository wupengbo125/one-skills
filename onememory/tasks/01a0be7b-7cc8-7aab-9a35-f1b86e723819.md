# 2026-09-20 检索脚本中文匹配与英文词干改造（会话 01a0be7b）

## 背景诉求
用户看到 tobi/qmd（Node 本地混合检索）后问：我们的 fts.py 能不能用它的方式，能不能改到和它一样。
用户随后明确边界：
- 只做 BM25，向量/embedding/LLM 重排一个字不要提——语义层由 Agent 自己承担（搜不到 apple 就搜苹果、逐个打开文件），这是"比向量更高级的向量"。
- 换引擎不许动业务面（不改 hooks、不改 references），脚本自身是缝。

## 排查过程
1. 装了 qmd 2.8.3（`npm i -g @tobilu/qmd`），实测中文 BM25 可用，英文词干、输出格式更全，但比 fts.py 慢（Node 启动 ~0.5s）。
2. 犯过的错：把三个数据仓建成同一个 qmd 全局索引的三个 collection，导致不带 `-c` 时一条查询跨仓搜全盘，且 BM25 的 IDF 语料统计被三仓混合，排序也变了。用户当场指出。结论：范围隔离是硬要求，一仓一库不能合。
3. 模型侧不可用：huggingface.co 不可达，hf-mirror.com 也 308 跳回 hf.co，GGUF 下不来；本机 4 核/7G/无 GPU。故 qmd 的加分项在此机器上不存在。
4. 读 qmd 源码定位它中文好的原因（dist/store.js:700-760、840-845）：索引期把 CJK 逐字空格化，查询期把 CJK 转 phrase 查询；FTS5 用 `porter unicode61`。BM25 索引是文档级（`documents` 表 `UNIQUE(collection, path)`，body 全文）。

## 关键决策
- 不引入 qmd 依赖，把它的 BM25 手法搬到 fts.py（纯标准库）。
- 保留我们比他好的部分：条目级索引粒度（`##`/列表项一行，BM25 不被长文稀释，命中直接给小节）、零依赖、速度快、一仓一库。
- 取舍：原 bigram+OR 是"宽召回"，会出现乱序误命中（搜「牛肉拉面」，文中只有「牛肉」也命中）；phrase 是"精确"。因 Agent 搜不到会自己改词重试，精确更值钱，故换 phrase。

## 代码结论
改动集中在 `one-wiki|one-memory|one-life/scripts/fts.py`（三份必须 md5 一致）：
1. `_expand_cjk` → `_space_cjk`：只输出单字空格（去掉 bigram）。
2. 建表 `tokenize='unicode61'` → `'porter unicode61'`（抽出 `FTS_TOKENIZE` 常量）。
3. 新增 `index_stale()`：索引缺失或旧分词器时判过期；`cmd_search` 改为按它触发全量重建（否则旧库跑新分词会静默漏召回）。
4. 查询构造：中文段由 "OR of bigrams" 改为整段 phrase `"牛 肉 拉 面"`，段间仍 AND。

## 验证
- 命中回归：牛肉拉面/艾宾/心即风水/止损 风控 均正常，`艾宾` 仍能命中 `艾宾浩斯`（phrase 前缀子串可中）。
- 误命中消除：搜「风止损」「止风损」零命中（旧逻辑会因 bigram「止损」命中）。
- 英文词干：搜 `contexts`（语料出现 0 次）能命中只含 `context` 的文档。
- 三仓 rebuild 通过：one-llmwiki 2111 条、one-hippocampus 319 条、one-life 13 条。

## 涉及产物
- `one-skills/{one-wiki,one-memory,one-life}/scripts/fts.py`（md5 efc3df28…）
- `one-skills/CODE_WIKI.md`：检索栈、自动重建行为、分词与查询构造三处描述同步
- 未动：hooks、references、one-scrolls/scripts/scrolls.py（另一套实现，同样有 bigram 弱点，本次未纳入）
- 环境：qmd 试用后已彻底清理（删 3 个 collection、`npm uninstall -g @tobilu/qmd`、删 `~/.cache/qmd` 与 `~/.config/qmd`）；结论是不引入 Node 依赖，三份 fts.py 保持解耦、不合一、不加 onefts 命令

## 第二轮：查询入口的意图分流与目录结构（2026-09-20 21:16）

「最近有什么笔记」「我有没有美食相关的东西」这类问句用 fts.py 搜不到："最近"不是内容词、日期只在路径里；"美食"是领域名，只出现在 `index.md` 与目录名里。另一个 Agent 实测失败后复盘：它不知道仓库结构，自己拼路径 `~/onespace/github/one-llmwiki/food`，漏了 `onewiki/` 层。

### 关键决策
- **落点**：不进 `SKILL.md`（用户明确否决），也不写进人读的 `readme.md`（技能与 readme 无关）。最终落在 `references/query.md` 与 `read-memory.md`——查询流程唯一必读的那份，正是那个 Agent 读过的文件。

## 第三轮：宪法提交台词的歧义修正（2026-09-20 21:26）

用户在 `one-agents.md` 里改「提交代码并更新记忆」这行时，担心台词在 worktree 场景下不稳，让我审。查出四处：

1. "每次问用户是否需要提交"后面紧跟"然后必须必须提交" —— "问"被写成了空动作，Agent 很可能问完就自己交了。改成"同意才提交"。
2. "如果是 worktree分支，则不执行本规则" —— "本规则"指代不清：是不问，还是问但不交？改成"worktree 下不问不提交"。
3. "只有合并到主干才执行"与"用户说 ddd 则合并"是并列两句，关系不明，Agent 可能把任意一次合并都当触发点。串成一条链：ddd → 合并 → 关 Issue → 删 worktree → 回主干仓写记忆 → 提交 push → 汇报。
4. 没写执行位置 —— 删 worktree 之后写记忆与提交必须在**主干仓**里做，否则会在 worktree 目录里写记忆、再往主干提交。这条是最容易翻车的，已补上。

用户还要求台词不许变长（上下文预算有限），最终版比原文短约 30 字，四条全修。

产物：`one-agents.md` 一行。未落 `onememory/rules.md` —— 该内容在宪法文件里已权威存在，按排除清单第 3 条（其他文档已有则不重复记录）跳过。
