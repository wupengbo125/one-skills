# derp-20260919-a1 · 自建自定义 DERP 中继（经公共 FRP 暴露）

## 背景诉求
本机 `one` 是 `MappingVariesByDestIP: true` 的对称 NAT，打洞成功率低，家里设备（Windows `redmi-w`、iPhone、Android）长期走官方 DERP `lax` 175ms。机器上已有一条公共 FRP 通道（`192.140.188.104`，本机到它只有 25ms）。诉求：让 Tailscale 借用这条 FRP 通道当中继。

## 方案取舍
- 官方明确说自定义 DERP "must not be behind NAT/load balancer"，FRP 正是反向代理 → 属于文档不支持的用法，但纯 TCP 透传不影响 HTTP upgrade，实测可跑
- 证书是最大障碍：公网入口是 `IP:8443` 无域名、拿不到 80 端口 → ACME 不可用；最终用**自签 IP 证书 + `CertName` 证书 pinning**，绕开所有平台装 CA 的麻烦（iOS/Android 也能用）
- 用户无域名、客户端主要是 Linux/Windows —— 但 pinning 方案让移动端也顺带可用

## 排查过程（关键转折）
1. 一开始按"买 VPS 更稳"建议，被用户要求必须给出能走的路 → 实测 FRP 服务器 25ms，确认值得做
2. derper 镜像拉不到（ghcr 走 IPv6 被 reset、Docker Hub 被墙）→ 改自编译（aliyun Go 镜像 + goproxy.cn）
3. derper 启动即退出：`-c <config path> not specified` → 新版非 root 必填，配 `StateDirectory` 解决
4. frpc 报 `proxy_not_found` → 该 FRP 是**面板型**，隧道必须在网页先建，frpc 里的 remotePort 无效
5. 我臆造了 `one_derp:10002`，而用户给的是 `tailscale_derp:8443` → 被斥；教训已入 rules.md
6. 试 `STUNPort: -1` 关 STUN → region 从 netcheck 候选消失、回落 sfo，回滚保留 3478
7. Windows 走中继时 SSH 连不上 → ping 各尺寸都通排除 MTU；定位到 derper 默认 `tcp-user-timeout=15s` 在拥塞链路上主动掐连接，放宽到 60s
8. 健康告警"IP forwarding disabled" → 本机 advertise 了 `::/0`，开 IPv6 转发后消失

## 代码/配置结论
- `/etc/systemd/system/derper.service`：`-hostname=192.140.188.104 -certmode=manual -certdir=/etc/derper -a=127.0.0.1:8443 -stun-port=3478 -http-port=-1 -tcp-user-timeout=60s -tcp-write-timeout=60s -c=/var/lib/derper/derper.key`，`DynamicUser + SupplementaryGroups=docker + StateDirectory=derper`
- `/home/ctyun/frp/frpc.toml`：追加 `tailscale_derp`(tcp 8443) 与 `tailscale_stun`(udp 3478)，并补上漏掉的 `[[proxies]]` 头
- tailnet ACL：`derpMap.Regions["900"]`，`DERPPort 8443 / STUNPort 3478 / CertName sha256-raw:05b614b1...`，经 API PATCH（带 `If-Match` etag，HuJSON）
- `/etc/sysctl.d/99-tailscale.conf`：`ip_forward=1` + `ipv6.conf.all.forwarding=1`（持久化）
- 证书指纹由 derper 启动日志直接给出，抄进 CertName 即可

## 遗留
- 免费 FRP 可能限速，大流量场景需测速；若不够换带公网 IP 的 VPS 装 derper（那时可开 `--verify-clients`）
- 经 FRP 的 STUN 会让本机误报公网 endpoint 为 `127.0.0.1`，对称 NAT 场景无害，未处理
