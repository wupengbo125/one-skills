# 87efa021-7b0f-4f39-b100-7f246323f1bb — one-todo 马身上的属性归位

## 背景诉求
用户发现：本地模式放两匹马跑在同一个工作区，归档一匹后卡片仍显示两个 agent；
再加一个审核员后，工作区里"还是两个、只是名头换了"。
用户判断这是"属性值不够，就抽到某个主干地方存"的设计病（本该属于马的属性被存成了待办级的平行名单），
要求查出同类毛病并分刀修掉。全程"评审反馈 → aaa → 整改"循环推进。

## 排查过程（关键事实）
- 卡片副标题读的是"建单时配的马名单"，归档只从"没跑完"名单摘人，主名单不动 → 数字不减、跳转箭头指死马。
- 待办里原本存了三条平行名单：全部会话号 / 终端号 / 待跑会话号；分支工作区另存一张表（还抄了马的提供商/模型/会话号）。
  "哪匹马＝哪个会话"靠位置或倒序猜，本地模式更是只能"取最后一个"。
- 评审回传在本地模式用"取名单最后一个会话"，可能发到别的马或已关会话；只有赛马按分支编号对号。
- 工作区号一个字段两种意思：本地模式＝马住的屋，赛马模式＝审核员落脚的主干。

## 关键决策
- 把"马自己的东西"全部搬到马身上：会话号（agentId/terminalId）、住处（workspaceId/branch/dir）、
  永久号（no，只增不减，分支名和评审编号都用它）。
- 删掉三条平行名单和分支工作区表；"哪匹马＝哪个会话"只认马身上的会话号。
- 工作区号只留一个意思：待办级＝主工作区（审核员落脚）。
- 发回只认"这次审的是哪一匹"（记会话号）；结论里的"胜者第几"只在发送时按马的号翻译一次。
- 每匹马一条自己的分支只认赛马模式；普通模式的分支是用户手填的，不给划、不误出赛马评比。
- 老数据一次性搬家（用户先前说过零兼容，但正在跑的老单子会"永不收工"，评审判为阻塞 → 补搬家）：
  会话号按"会话/终端"分别对号（旧代码就是分开 push 的），分支工作区先按会话号认、
  再按旧分支名里的号（＝当年名单上的位置），最后兜底；搬完删旧字段。

## 代码结论（改动面）
- 马（agents[]）：spawnedAt / no / agentId / terminalId / workspaceId / branch / dir；新增 nextNo（发号水位，只增不减）。
- 删：agentIds / terminalIds / pendingAgentIds / worktrees / todoWorktreeItemSchema / 评审里的 targetIndex。
- 归档一匹马＝从名单划掉；工作区归档＝住在里面的马一起走（按马的 workspaceId 认）。
- 评审候选＝一匹马一条（编号＝马的号）；发回：先按 targetId 认马，赛马多马时按"胜者 N"→ 号找马，找不到就报错不猜。
- 界面：候选不止一匹（活着）时必须自己选；选中记会话号不记位置；✕ 只在赛马模式出现；失败路径也存发号水位。

## 验证
- typecheck（tsc --noEmit）每刀均过。
- 搬家拿本机 55 条真实待办只读复跑：旧字段残留 0、丢会话 0、重号 0、nextNo 不小于旧分支号、跑两遍结果一致；
  正在跑的老单子（含赛马单）都把马和它的分支对上了。
- 未跑运行时（插件由 Paseo 加载），交互层面的验证留给用户在界面点。
