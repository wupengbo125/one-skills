# 轻量审查开发流程 (Harness Light Directive)

当你在本会话中需要**修改代码、配置或业务文件**时，必须严格执行轻量审查流程（若当前会话已调用重型 `one-harness`，则跳过本流程）：

## 核心流程六步走
1. **改动前准备**：确保 Git 仓库工作区干净（`git status` 无未提交的脏改动），保证后续 diff 纯净。
2. **主 Agent 直接修改**：主 Agent 亲自编码，严守需求边界，只改需求直接要求的内容，坚决不增删无关联代码。
3. **写完禁止直接提交**：文件修改完成后**切勿直接 `git commit`**，保持工作区处于未暂存/未提交的 diff 状态。
4. **必须派全新 Sub-agent 审查（铁律）**：
   - 使用 `subagent` 工具派生无记忆独立 Sub-agent。
   - 审查输入：①用户原始诉求（目标与非目标）；②`git diff HEAD`（本次全部代码改动）。
   - 核心审查指标：**需求与改动是否严格画等号**：
     - 是否改多了？（Diff 包含了用户没提的额外变动）
     - 是否改少了？（用户明确要求的改动有遗漏）
     - 功能是否一致？（实现逻辑是否与需求完全契合）
   - 若审查不通过：主 Agent 修复问题后重新派 Sub-agent 复审，直至通过。
5. **判断是否同步活蓝图**：
   - 主 Agent 自检：本次改动是否涉及业务功能、规则、逻辑或架构变化？
   - 若是：同步增量更新全局业务活蓝图（`BLUEPRINT.md` 或 `docs/BLUEPRINT.md`）。
   - 若否（纯格式、变量名、轻微注释等微调）：跳过蓝图更新。
6. **交付与提交**：
   - 审查通过且蓝图确认后，方可执行 `git commit`。

## 负向抑制规则 [何时不触发]
- `[READ_ONLY]`：仅阅读代码、查看文件、解释代码、回答知识类问题 → 不触发。
- `[TEMP_DEBUG]`：排查中仅运行非破坏性命令、打印日志 → 不触发。
